# Section 1.6: Higher-Order Functions

## Core Idea
Without function definition we would always work "at the level of the particular operations that happen to be primitives in the language … Our programs would be able to compute squares, but our language would lack the ability to express the concept of squaring." A powerful language must let us assign names to common *patterns* and work in terms of those names directly. Patterns that recur across code but are used with different functions can themselves be abstracted — by functions that accept functions as arguments or return functions as values. "Functions that manipulate functions are called higher-order functions"; they vastly increase the expressive power of the language.

## Frameworks Introduced

### Functions as Arguments (the summation abstraction)
`sum_naturals`, `sum_cubes`, and `pi_sum` "clearly share a common underlying pattern. They are for the most part identical, differing only in name and the function of k used to compute the term to be added." Each could be generated by filling slots in one template:
```
def <name>(n):
    total, k = 0, 1
    while k <= n:
        total, k = total + <term>(k), k + 1
    return total
```
"The presence of such a common pattern is strong evidence that there is a useful abstraction waiting to be brought to the surface." We want to express *the concept of summation itself*, not only particular sums — so transform the slots into formal parameters (`summation(n, term)`).

### Functions as General Methods (iterative improvement)
Some functions "express general methods of computation, independent of the particular functions they call." The environment model extends **without change**: formal parameters are bound to argument values (which may be functions) in a new local frame. The iterative improvement algorithm: begin with a `guess` of a solution; repeatedly apply an `update` function to improve it; apply a `close` comparison to check whether the guess is "close enough":
```python
def improve(update, close, guess=1):
    while not close(guess):
        guess = update(guess)
    return guess
```
`improve` is "a general expression of repetitive refinement" that doesn't specify the problem — those details live in `update` and `close`. Two big ideas the golden-ratio example illustrates: (1) naming and functions abstract away vast complexity — trivial definitions set an intricate process in motion; (2) only because we have an extremely general evaluation procedure can small components compose into complex processes.

### Lexical Scoping (nested definitions)
Passing functions as arguments has two downsides: the global frame becomes cluttered with names of small functions (which must all be unique), and we are constrained by particular signatures (`improve`'s `update` must take exactly one argument). **Nested function definitions** solve both. Like local assignment, local `def` statements only affect the current local frame; they aren't even evaluated until the enclosing function is called. Locally defined functions have access to the name bindings in the scope in which they are *defined* — this discipline is **lexical scoping**: "the inner functions have access to the names in the environment where they are defined (not where they are called)."

**Two key advantages of lexical scoping**:
1. The names of a local function do not interfere with names external to the enclosing function (bound in the local environment, not global).
2. A local function can access the environment of the enclosing function, because its body is evaluated in an environment that extends the environment in which it was defined.

**Closures**: `sqrt_update` carries data with it — the value for `a` referenced where it was defined. "Because they 'enclose' information in this way, locally defined functions are often called *closures*."

### Functions as Returned Values
Locally defined functions maintain their parent environment when they are returned — this is what makes function **composition** definable: `compose1(f, g)` returns `h(x) = f(g(x))` (the `1` signifies single-argument composed functions; a naming convention only, not enforced). "No modification to our environment model is required to explain our ability to return functions in this way."

### Currying
Transform `f(x, y)` into `g` such that `g(x)(y)` is equivalent to `f(x, y)`. Haskell permits only single-argument functions, so everything is curried; in Python, currying is useful when an interface requires a single-argument function — e.g., the **map pattern**, which applies a single-argument function to a sequence of values. `curry2(f)(x)(y) == f(x, y)`; `uncurry2(curry2(f))` is equivalent to `f`.

### Lambda Expressions
Create function values on the fly, unnamed: a lambda expression evaluates to a function whose body is **a single return expression; assignment and control statements are not allowed**. Reading template: `lambda x: f(g(x))` = "A function that takes x and returns f(g(x))". The result is a *lambda function* — no intrinsic name (Python prints `<lambda>`; diagrams use λ), otherwise an ordinary function. Style: "Python style prefers explicit def statements to lambda expressions, but allows them in cases where a simple function is needed as an argument or return value." The name is a typographic accident (Church's hat ŷ → Λ → λ — Norvig's account); lambda calculus returns in Chapter 3.

### Abstractions and First-Class Functions
Be alert to underlying abstractions, build on them, generalize — but "expert programmers know how to choose the level of abstraction appropriate to their task." Elements with the fewest restrictions have **first-class status**; the "rights and privileges" of first-class elements:
1. They may be bound to names.
2. They may be passed as arguments to functions.
3. They may be returned as the results of functions.
4. They may be included in data structures.
"Python awards functions full first-class status, and the resulting gain in expressive power is enormous." The significance of higher-order functions: they let us represent general methods explicitly as elements in the language, handled like any other computational element.

### Function Decorators
`@trace` above `def triple(x)` affects the execution rule for `def`: the function is created as usual, but the name `triple` is bound not to it — instead to the returned value of calling `trace` on the newly defined function. Equivalent code: `triple = trace(triple)` after a plain `def`. Used in the book's projects for tracing and for selecting which functions run from the command line. *Extra for experts*: `@` may be followed by a call expression — it is evaluated first, the `def` second, then the decorator result is applied to the new function and bound to the name.

## Evaluation Rules (the model's extensions, verbatim-faithful)

**Two extensions to the environment model that enable lexical scoping**:
1. Each user-defined function has a **parent environment**: the environment in which it was defined.
2. When a user-defined function is called, its local frame **extends** its parent environment.

**Parent annotation**: the parent of a function value is the first frame of the environment in which that function was defined (functions without annotations were defined in the global environment). When a user-defined function is called, the frame created has the same parent as that function. The most critical step in the `sqrt` evaluation: the transfer of `sqrt_update`'s parent to the frame created by *calling* `sqrt_update` (annotated `[parent=f1]`).

**Extended environments**: an environment can consist of an arbitrarily long chain of frames, always concluding with the global frame. Before `sqrt`, environments had at most two frames. Name lookup finds the first value bound to the name in the current environment, following the chain: for `a` inside `sqrt_update`, Python checks the `sqrt_update` frame (no `a`), then the parent frame `f1`, finding `a` = 256.

## Key Concepts
- **Higher-order function**: accepts functions as arguments or returns them as values.
- **Common-pattern template**: a family of near-identical functions generated by filling slots → parameterize the slots.
- **Iterative improvement**: guess / update / close — a general method.
- **Parent environment / extended environment / frame chain**: the lexical-scoping machinery.
- **Closure**: a locally defined function that encloses data from its defining environment.
- **Function composition**: `compose1(f, g)(x) = f(g(x))`.
- **Zero of a function**: an argument yielding return value 0; degree-n root of a = the x with xⁿ − a = 0, so root-finding reduces to zero-finding.
- **Newton's method**: iterative improvement for finding zeros of any *differentiable* function (approximable by a straight line at any point); follows tangent lines to 0. The tangent's slope is the derivative; translating x by f(x)/slope gives where the tangent touches 0.
- **Currying / uncurrying**: multi-argument ↔ chain of single-argument functions.
- **Map pattern**: apply a single-argument function to a sequence of values (`map_to_range`).
- **Lambda function**: unnamed, single-expression function.
- **First-class status**: the four rights and privileges.
- **Decorator**: `@expr` = bind the def'd name to `expr(new_function)`.

## Mental Models
- **Fill-in-the-template test**: if several functions can be generated by filling slots in one template, parameterize the slots.
- **Closure = code + defining environment**: a returned inner function is a package that runs anywhere yet still sees `a`.
- **Nest when the interface is narrow**: `improve` demands a one-argument `update`; your logic needs `a` too — capture it lexically rather than widening the signature or using globals.
- **Lambda as expression-level def**: fine as an argument or return value; name anything bigger.
- **Layered generality**: improve → find_zero → nth_root_of_a — each higher-order layer adds generality without touching the layers below.

## Anti-patterns
- **Copy-pasting near-identical loop functions** instead of writing `summation(n, term)` once.
- **Cluttering the global frame** with tiny helper functions whose names must all be unique — nest them.
- **Compound lambda expressions**: `compose1 = lambda f,g: lambda x: f(g(x))` is correct but "notoriously illegible, despite their brevity."
- **Maximal abstraction for its own sake**: "This is not to say that one should always write programs in the most abstract way possible."
- **Assuming Newton's method always converges**: it will not always converge — the initial guess must be sufficiently close to the zero, and various conditions about the function must be met. (Still, variants power very fast algorithms for logarithms and large integer division in modern computers.)

## Code Examples
The three sums and their abstraction:
```python
def sum_naturals(n):
    total, k = 0, 1
    while k <= n:
        total, k = total + k, k + 1
    return total              # sum_naturals(100) -> 5050

def sum_cubes(n):
    total, k = 0, 1
    while k <= n:
        total, k = total + k*k*k, k + 1
    return total              # sum_cubes(100) -> 25502500

def pi_sum(n):                # sums 8/((4k-3)(4k-1)); converges to pi slowly
    total, k = 0, 1
    while k <= n:
        total, k = total + 8 / ((4*k-3) * (4*k-1)), k + 1
    return total              # pi_sum(100) -> 3.1365926848388144

def summation(n, term):
    total, k = 0, 1
    while k <= n:
        total, k = total + term(k), k + 1
    return total

def cube(x):
    return x*x*x
def sum_cubes(n):
    return summation(n, cube)        # sum_cubes(3) -> 36
def identity(x):
    return x
def sum_naturals(n):
    return summation(n, identity)    # sum_naturals(10) -> 55
summation(10, square)                # 385 — callable directly too
def pi_term(x):
    return 8 / ((4*x-3) * (4*x-1))
def pi_sum(n):
    return summation(n, pi_term)
pi_sum(1e6)                          # 3.141592153589902
```
Iterative improvement and the golden ratio:
```python
def improve(update, close, guess=1):
    while not close(guess):
        guess = update(guess)
    return guess

def golden_update(guess):
    return 1/guess + 1
def square_close_to_successor(guess):
    return approx_eq(guess * guess, guess + 1)
def approx_eq(x, y, tolerance=1e-15):
    return abs(x - y) < tolerance

improve(golden_update, square_close_to_successor)   # 1.6180339887498951

# testing against the closed form:
from math import sqrt
phi = 1/2 + sqrt(5)/2
def improve_test():
    approx_phi = improve(golden_update, square_close_to_successor)
    assert approx_eq(phi, approx_phi), 'phi differs from its approximation'
improve_test()   # no news is good news: returns None on success
```
Nested definitions, closures, composition, currying:
```python
def average(x, y):
    return (x + y)/2

def sqrt(a):
    def sqrt_update(x):
        return average(x, a/x)
    def sqrt_close(x):
        return approx_eq(x * x, a)
    return improve(sqrt_update, sqrt_close)
sqrt(256)   # 16.0

def compose1(f, g):
    def h(x):
        return f(g(x))
    return h
square_successor = compose1(square, successor)
result = square_successor(12)   # 169 — names f and g resolve correctly
                                # even with a conflicting global f

def curried_pow(x):
    def h(y):
        return pow(x, y)
    return h
curried_pow(2)(3)   # 8

def map_to_range(start, end, f):
    while start < end:
        print(f(start))
        start = start + 1
map_to_range(0, 10, curried_pow(2))   # prints 1 2 4 ... 512

def curry2(f):
    """Return a curried version of the given two-argument function."""
    def g(x):
        def h(y):
            return f(x, y)
        return h
    return g
def uncurry2(g):
    """Return a two-argument version of the given curried function."""
    def f(x, y):
        return g(x)(y)
    return f
pow_curried = curry2(pow)
pow_curried(2)(5)             # 32
uncurry2(pow_curried)(2, 5)   # 32
```

## Worked Examples

### 1. summation → pi_sum
Spot the template across the three sums; the only varying slot is the term function of k. Define `summation(n, term)`; define `pi_term(x) = 8/((4x−3)(4x−1))`; then `pi_sum(n) = summation(n, pi_term)` and `pi_sum(1e6)` → 3.141592153589902 (1e6 = 1×10⁶). Binding `cube` to local name `term` in `sum_cubes(3)` ensures 1+8+27 = 36 is computed correctly — the argument function travels through the local frame like any value.

### 2. improve → golden ratio, with the environment trace
`improve(golden_update, square_close_to_successor)`: a local frame for `improve` binds `update`, `close`, and `guess`=1 (default). In the body, `close(guess)` calls `square_close_to_successor(1)` → `approx_eq(1, 2)` → False; so `guess = update(guess)` → `golden_update(1)` = 2; loop continues (2²=4 vs 3, …) until guess·guess ≈ guess+1 within tolerance → 1.6180339887498951. Correctness is tested against the exact closed form φ = 1/2 + √5/2 via `improve_test()`.

### 3. sqrt(256) and the three-frame chain
`sqrt_update(x, a)` as a two-argument global function is incompatible with `improve` (takes two arguments, provides only one update). Nesting fixes it: calling `sqrt(256)` creates frame f1 binding a=256 and *then* evaluates the inner `def`s, creating functions whose parent is f1. `improve` receives `sqrt_update`; applying it to guess 1 creates a frame containing only `x` **with parent f1** — the critical transfer. Looking up `a`: not in `sqrt_update`'s frame; found in f1 as 256. Environment = [sqrt_update local, f1, global]. Repeated `average(x, a/x)` updates converge; `sqrt_close` checks `approx_eq(x*x, a)`; result 16.0.

### 4. Newton's method, end to end
Zeros: arguments where a function returns 0; finding one often solves another problem (square roots). The method works for any differentiable function by following tangent lines:
```python
def newton_update(f, df):
    def update(x):
        return x - f(x) / df(x)
    return update

def find_zero(f, df):
    def near_zero(x):
        return approx_eq(f(x), 0)
    return improve(newton_update(f, df), near_zero)

def square_root_newton(a):
    def f(x):
        return x * x - a
    def df(x):
        return 2 * x
    return find_zero(f, df)
square_root_newton(64)   # 8.0

def power(x, n):
    """Return x * x * x * ... * x for x repeated n times."""
    product, k = 1, 0
    while k < n:
        product, k = product * x, k + 1
    return product

def nth_root_of_a(n, a):
    def f(x):
        return power(x, n) - a
    def df(x):
        return n * power(x, n-1)
    return find_zero(f, df)
nth_root_of_a(2, 64)   # 8.0
nth_root_of_a(3, 64)   # 4.0
nth_root_of_a(6, 64)   # 2.0
```
√a is the x with x²−a = 0; generally the degree-n root of a is the x with xⁿ−a = 0, using df(x) = n·xⁿ⁻¹ from calculus. Approximation error in all of these is reduced by shrinking `tolerance` in `approx_eq`. Three layers each add generality: `improve` (any repetitive refinement) → `find_zero` (any differentiable f) → `nth_root_of_a` (any degree, any a).

## Common Errors (what the author explicitly warns about)
- Newton's method non-convergence: bad initial guess or unmet conditions on the function.
- Compound lambdas: legal but notoriously illegible — prefer `def`.
- Expecting the `1` in `compose1` to be enforced — it's only a name.
- Forgetting that local `def`s are not evaluated until the enclosing function is called.
- Confusing where a closure looks for names: the *defining* environment, never the calling one.

## Key Takeaways
1. A repeated template across functions is an abstraction waiting to be named (summation, improve); parameterize the slots.
2. Lexical scoping = two model rules: every function records its parent (defining) environment; every call's frame extends that parent. Environments become chains ending at the global frame.
3. Closures let you fit extra data through narrow interfaces (one-argument `update`) without globals or clutter.
4. Returned functions need no new machinery — the environment model explains them as-is.
5. `curry2(f)(x)(y) == f(x, y)`; currying serves single-argument interfaces like the map pattern.
6. Reserve lambda for simple functions used as arguments or return values; a lambda body is one return expression, no statements.
7. First-class functions (bind, pass, return, store) are what let general methods be ordinary values.
8. `@decorator` is just `name = decorator(name)` after the `def`.
